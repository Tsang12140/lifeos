# 照片文字识别（OCR）选型与实现方案

> 起点：2026-10-15 蛋妞看到苹果相册能搜照片正文，提出「是不是多铺了一层 OCR、不耗 token」。
> 约束：正式部署在**宝塔（Linux，4 核 4G）**、上面还跑着别的项目 ⇒ 不能占服务器性能。
> 关联：第 ② 层（照片描述字面并入检索）已于 2026-10-15 完成并验证通过，纯 SQLite、跨平台，**不受本方案影响**（见 `docs/photo-search-worklog.md`）。

## 1. 一句话结论

苹果那层是**设备端 OCR，确实不花 token** —— 判断成立；但**服务器上没有「系统自带、0MB」的 OCR 这条路**（那是 Windows 独有的能力，Linux 没有等价物）。

D4 解锁之后，取舍已经很清楚：

> **① 云 OCR**（最准、服务器 ≈0、几百张落免费额度、**照片可出门**）＋ **③ 系统 tesseract**（完全离线、零成本、印刷体够用）**并存** —— 前者是主路，后者是「无 AI key / 断网也能用」的兜底（对齐既有红线）。

## 4. 关键数字（查证过，非估算）

**腾讯云 OCR（方案 ①）**

- 接口：`POST https://ocr.tencentcloudapi.com`，`Action=GeneralBasicOCR`、`Version=2018-11-19`（高精度版为 `GeneralAccurateOCR`）。
- 通用印刷体识别：**每月 1000 次免费额度**，每月 1 号发放、当月有效、不累积。
- 后付费阶梯：< 1 万次 **0.15 元/次**；1 万–10 万次 **0.10**；10 万–100 万次 **0.06**。预付费资源包：1000 次 120 元；1 万次 800 元。**高精度版更贵**（0.50 / 0.35 / 0.20 元/次）。
- **识别准确率（官方标称）：通用印刷体 96%，高精度版 99%** —— 高精度版正对口「文字较多、长串数字、小字、模糊字、倾斜文本」。
- **图片输入约束（官方文档）**：`ImageBase64` 经 Base64 编码后 **≤ 10MB**；**分辨率建议 600×800 以上**；支持 **PNG / JPG / JPEG / BMP / PDF** —— **未列 WebP**。
  ⚠️ **本项目派生缩略图是 WebP**（`derived-thumbs.ts`），所以送 OCR 前**必须转成 PNG/JPEG**（项目已用 `sharp`，零成本）。
- 频率限制：通用印刷体 **20 次/秒**（账号维度）。
- ⚠️ **部分失败调用的错误码也计费** —— 接入前必须做图片前置校验。
- ⚠️ Region 选到境外（含中国香港、中国澳门、中国台湾、新加坡等）按国际站计费、**不扣国内资源包**。
- ⚠️ **后付费默认不开**：额度用尽后调用直接失败（不会偷偷扣费）；若开了后付费，超额自动计费。**建议保持关闭。**

> **对你特别相关**：全库照片大概几百张，**一次性补 OCR 就落在每月 1000 次免费额度内**；之后每月新增远达不到 1000 张 ⇒ **很可能长期 0 成本、0 服务器占用**。D4 已允许非私密照片出服务器 ⇒ **这条路解锁，且是精度最高的那条。**

**tesseract（方案 ③ / ④）**

- 核心引擎 ~10MB；中文语言包 fast 版 1–5MB、best 版 10–20MB。
- 运行时内存 50–200MB；CPU 单张 150–300ms（③ 跑完即释放，④ 跑在你进程里）。
- 中文准确率约 89%（对比 PaddleOCR 的 95%+）；**印刷体（书页、菜单、小票、包装盒）够用，手写体和艺术字明显不行。**

**PaddleOCR / RapidOCR（方案 ⑤，已淘汰，留档）**

- 空载常驻 450MB、初始化 2.1s；4 核 4G 实测：640×480 → 0.8s / 1.3GB；1920×1080 → 2.1s / 2.8GB。
- 模型本体不大（检测 3.5MB + 识别 12MB），**大头是运行时内存**。

## 5. 隐私红线 → 落地结论（D1，已定；**已核查现有代码**）

**① 生成侧：私密记录绝不送去识别。**
- AI 描述**已经满足**：`apps/api/src/photo-description.ts:274` 在 `record.isPrivate === true` 时直接 `skippedPrivate += 1; continue`，照片**根本不上传**（源码注释就写着 *Private records are never sent. That is the owner's red line.*）。
- **OCR 必须照抄这一条** —— D1 的硬要求。OCR 与 AI 走**同一道门**（同一个循环、同一个 `continue`）。

**② 事后转私密：不删产物，只把「检索门」交给隐私锁。** 蛋妞 2026-10-15 23:3x 定的三件事：

| 事项 | 结论 |
| --- | --- |
| 已生成的产物（描述 / 将来 OCR 文本） | **不删** —— 「既然都得出了，就留着，别浪费」 |
| 检索门 | **跟隐私锁**：锁**打开**时可检索到私密；锁**关闭**时不允许搜到 |
| 私密的主防线 | **流程，不是代码** —— 每天识别 + OCR **只跑一次**；在定时前把该转私密的转掉，它们根本不会被识别 |

**核查结论：这条语义，现有代码就已经是这样。**

| 环节 | 事实 | 位置 |
| --- | --- | --- |
| 生成 | 私密直接 `continue`，照片不出去 | `photo-description.ts:274` |
| 显示 | `privacyShown \|\| record.isPrivate !== true` ⇒ **锁关不显示、锁开显示** | `main.tsx:1773` |
| 搜索请求 | 主搜索（`queryPath`）**不带** `includePrivate`；只有「接近结果」带 `includePrivate=1`（当隐私开着） | `main.tsx:618-654`、`search-alternatives.tsx:33` |
| 服务端过滤 | `list()` 与路由 `entityMatch=any`（普通关键词搜索）**都不过滤私密**；只有 `near` / `calendar=1` 两条分支过滤 | `repository.ts:1693`、`routes-records.ts:136` |

⇒ **② 层的描述并入没有开出新的泄露类别**：私密记录的**正文**本来就参与匹配、靠前端的隐私锁挡住，描述走的是同一个门。**OCR 文本走同一道门，同样不新增类别。**

**一个可选加固（倾向不做）**：锁关着时，服务端**仍会把命中的私密记录（含描述/OCR 文本）发给前端**，只是前端不画。若要「连服务端都不返回」，需把 `includePrivate` 接进关键词搜索的 WHERE；**代价**是 `main.tsx:1807` 那个「这次筛选有 N 条隐私记录符合条件，要现在看吗？」提示会失效（它正是靠拿到这些记录才数得出 N）。

**已作废的方案**：原先写的「B 破坏式封印」（转私密即物理删描述）**与「不删产物」冲突，作废。**

## 6. 建议路线（D5：① 先行、③ 保底）

- **主路 ① 云 OCR**：最准、服务器 ≈0 占用、几百张落在 1000 次/月免费额度内；**照片可出服务器（D4，仅非私密）**。
- **兜底 ③ 系统 tesseract + CLI**：完全离线、零成本，对齐「**无 AI key 也要能用**」—— 云挂了 / 断网 / 没 key，它照跑（印刷体够用，~89%）。
- **② 浏览器端**：只做锦上添花（补不了历史照片）；**④ 不建议**；**⑤ 淘汰**。
- **形态**：**每天一次**定时批处理（识别 + OCR）。**跑之前先转私密 = 私密躲过的窗口**（D1 的主防线）。
- **落地前确认**：OCR 结果写**宝塔**那台（D3）—— 本机 `data/` 只是测试副本。

## 7. 激活清单：蛋妞要做的 4 步（腾讯云侧）

> 全程**不需要付费、不需要买资源包**。免费额度开通即自动发放。

**第 1 步 · 开通服务**
1. 打开 <https://console.cloud.tencent.com/ocr>（文字识别控制台）。
2. 阅读《文字识别服务条款》→ 勾选同意 → 点 **「立即开通」**。
3. 这一步**一键开通全部服务端接口**（通用文字、卡证、票据…），**不需要逐个申请**；免费资源包（通用类 1000 次/月）自动发到账号。
4. 看一眼 <https://console.cloud.tencent.com/ocr/package>（资源包管理）确认额度已到账。

> **⚠️ 那一长串品类不用你选（2026-10-16 蛋妞问到，附控制台截图）**
>
> 控制台列出的「通用文字识别（高精度版）／表格识别／广告文字识别／印章识别／身份证识别…」**不是让你挑一个开通** —— 开通是**一键全开**，每个接口**各自**带自己的免费额度。页面上每行「剩余免费 1000 次」正是证据：额度已经全发到手了。**那一页是「余额表」，不是「选项表」。**
>
> **真正「选品类」的地方在本项目代码里**，只有一个环境变量：`LIFEOS_TENCENT_OCR_ACTION`。
>
> | 控制台显示名 | 代码里的值（`..._OCR_ACTION`） | 我们要不要 |
> | --- | --- | --- |
> | 通用印刷体识别 | `GeneralBasicOCR` | ✅ **默认** |
> | 通用文字识别（高精度版） | `GeneralAccurateOCR` | ✅ 备选：小字 / 倾斜 / 模糊更准（**也有独立的 1000 次/月**，见下） |
> | 表格识别 / 广告文字识别 / 印章识别 / 身份证识别 / 通用文字识别 Agent / 名片识别… | —— | ❌ 一个都不碰：那些是**针对特定版式的结构化抽取**（如身份证要返回姓名字段），我们的场景只是「照片里有什么字」 |
>
> **不需要你记住这些名字** —— `.env` 那 4 行照抄即可。**万一填错也不出事**：腾讯云返回 `InvalidAction`（接口不存在），该错误码**不计费**；代码又把一切失败当 `null` 处理 ⇒ 最坏结果是「跑不出来」，不是「花钱」。
>
> **顺带**：截图里「通用文字识别 Agent（`RecognizeAgent`）」那行是「剩余免费 0 次」—— 那种属于**一次性发放**的品类，与我们无关，不用管。

**第 2 步 · 拿密钥**
1. 打开 <https://console.cloud.tencent.com/cam/capi>（访问管理 → API 密钥管理）。
2. 点 **「新建密钥」**，得到一对：
   - `SecretId`（`AKID` 开头）
   - `SecretKey`（**只在创建时完整显示一次**，务必当场复制）
3. **建议更安全的做法**：不要用主账号密钥（权限过大，泄露＝整账号风险）。改为「访问管理 → 用户 → 新建子用户」，只勾 **`QcloudOCRFullAccess`** 一个策略，用**子用户的密钥**。
4. ⚠️ 复制时注意**首尾不要带空格**（新手高频翻车点）。

**第 3 步 · 填进 `.env`**（两处都要：本机测试那份 + 宝塔线上那份）

```
LIFEOS_TENCENT_SECRET_ID=AKIDxxxxxxxxxxxxxxxxxxxxxxxx
LIFEOS_TENCENT_SECRET_KEY=xxxxxxxxxxxxxxxxxxxxxxxx
LIFEOS_TENCENT_OCR_REGION=ap-guangzhou
# 可选，默认就是它；想试高精度版改成 GeneralAccurateOCR
LIFEOS_TENCENT_OCR_ACTION=GeneralBasicOCR
```

- **Region 填什么？（2026-10-16 蛋妞问到）** 填 **`ap-guangzhou`**，**与「你的服务器在哪」无关** —— 它指的是「**把照片送去腾讯云哪个机房识别**」，不是「你的服务器所在区域」。OCR 是纯 API，照片经 HTTPS 传到腾讯云机房，宝塔服务器在国内还是国外都不影响这个参数。腾讯云 API 文档的原话：「建议域名和公共参数 Region 选择相同的地域：华南地区（广州），`ap-guangzhou`」。
- **唯一铁律：必须是国内地域。** 可填 `ap-guangzhou` 广州（推荐）/ `ap-shanghai` 上海 / `ap-beijing` 北京 / `ap-chengdu` 成都 / `ap-chongqing` 重庆 / `ap-nanjing` 南京。**绝不填境外**（`ap-hongkong` 中国香港 / `ap-singapore` 新加坡 / `ap-tokyo` 东京 / `na-siliconvalley` 硅谷…）—— 官方明确：选境外地域会**按国际站后付费计费、且不抵扣国内免费资源包**，那就是真花钱了。
- 密钥**不进 Git**（`.env` 已被 `.gitignore` 忽略；与现有 `BACKUP_S3_*`、`LIFEOS_DEEPSEEK_API_KEY` 同一套约定）。
- 宝塔那份：直接编辑站点目录下的 `.env`（LifeOS 的 `.env` 与 Clockin-B 无关，互不影响）。

**第 4 步 · 重启 API**
- 本机预览：重启预览服务即可。
- 宝塔：`cd /www/wwwroot/<lifeos 路径> && pm2 restart <应用名>`。

**额度用尽会怎样（已去腾讯云官方文档核准，2026-10-16）**

| 问题 | 答案 |

| **唯一的坑** | **别在控制台手动开「后付费」** —— 开了就不停了，超额自动按次计费（0.15→0.06 元/次）。若曾开过，去「设置页」<https://console.cloud.tencent.com/ocr/setting> 关掉。老账号（2021-12-14 前开通）默认是**自动开后付费**、必须手动关；我们不是老账号。 |

**额度怎么发放：「每月 1000 次」，不是「永久 1000 次」（2026-10-16 核准）**

- **每月 1 号自动发放 1000 次，当月有效、用不完不结转。** 官方原文：「以免费资源包的形式在每个月1号自动发放到您的腾讯云账号中，仅在当月有效」。新客户（当月首次开通）**开通后立即发放**；老客户从每月 1 号起发放。
- **是长期每月都有的，不是一次性**：唯一会暂停的情形是**连续 1 年未使用** OCR 产品（暂停每月发放，重新使用时 2 分钟内自动恢复）；另外**违禁停服或欠费停服期间不享受免费额度**，服务重开才恢复。
- **高精度版另有一份独立的 1000 次/月**（资源包名不同 ⇒ 不共享）⇒ **每月实际可用 2000 次，且对照测试免费**。
- 换算到我们：全库几百张**一次性补跑落在当月 1000 次内**；之后每月新增照片（一天几张）远不到 1000 张 ⇒ **长期零成本**。真超了也只是 Basic 0.15 元/次、高精度 0.50 元/次。

**应用侧现状 + 一个小缺口**

- 额度用尽后，`tencent-ocr.ts` 的识别器一律返回 `null`（设计如此：失败绝不能当成「这张图没有字」），该照片跳过、**不写错数据、不扣钱**、下一张继续。
- **缺口**：目前没有「熔断」—— 额度耗尽后，一次全库跑仍会为**每一张**照片各发一次注定失败的请求（只浪费一个网络往返，钱与安全均无碍）。
- **候选加固（约 10 行，待蛋妞点头）**：识别器一旦认出「资源包耗尽 / 欠费 / 服务未开通」这类**致命错误码**就抛出终止信号，`describePhotoLibrary` 接到后**本轮立即停手**，而不是把剩下的几百张白试一遍。判据只用错误码，不猜额度。

## 8. 实现设计：要动的 5 个文件（我这边做）

| 文件 | 改动 |
| --- | --- |
| `apps/api/src/tencent-ocr.ts`（**新增**） | TC3-HMAC-SHA256 签名（Node 原生 `crypto`，**零新依赖**）+ `GeneralBasicOCR` 调用；输入 JPEG/PNG buffer，输出拼接好的文本 |
| `apps/api/src/config.ts` | 读 3 个新 env（`LIFEOS_TENCENT_SECRET_ID` / `..._SECRET_KEY` / `..._OCR_REGION`）+ 可选 `..._OCR_ACTION`；缺 SecretId/SecretKey 时整个功能静默关闭 |
| `apps/api/src/photo-description.ts` | 同一张照片：**AI 出「意」+ OCR 出「字」**；OCR 文本作为**独立条目** `type:"photo-ocr"` 写进 `aiDerived`，与描述并存、互不覆盖；**共用同一道私密门**（`isPrivate` 已在外层 `continue`） |

| `apps/api/test/api.test.ts` | 注入 stub（**不联网**）：验证签名串、OCR 条目落库、搜索能命中 OCR 独有词、私密记录不产生条目 |

**三个必须遵守的技术约束（已核实）**

1. **送 OCR 的图不能是 WebP** —— 接口只列 PNG/JPG/JPEG/BMP/PDF。项目已用 `sharp`（`derived-thumbs.ts:5`），直接从原图编出 JPEG（或把 2048 缩略图转 JPEG），零新增依赖。
2. **`ImageBase64` ≤ 10MB、建议分辨率 ≥600×800** ⇒ 取 **2048 宽**（`THUMBNAIL_WIDTHS` 已有此档，是给放大预览用的），清晰、且远低于上限。
3. **AI 与 OCR 是两层不同的事，不互相替代**：AI 出「意」（概括，「一本摊开的书，含《江城子》等文字」），OCR 出「字」（逐字原文）。书页 / 菜单 / 小票 = OCR 的主场；无字照片（猫、饭碗）= AI 的主场。**两层并存。**

**为什么要「先 ① 后 ③」而不是直接 ③**：① 要花的是**腾讯云的免费额度**（几百张一次性跑完，之后每月新增远不足 1000），换来的是工业级精度；③ 的价值在于「**云不可用时它还在**」，属于韧性设计，不是精度升级。两者不冲突，可以先后落地。

**为什么默认 `GeneralBasicOCR` 而不是高精度版**：**两者各有独立的 1000 次/月免费额度** —— 资源包名不同即不共享（官方原文：「开通了多项文字识别服务的客户，各项服务均可享受对应额度的免费调用次数」；「通用印刷体识别、通用文字识别（高精度版）属于两个完全不同的接口，资源包不支持混用」）⇒ **拿同一批图跑两遍做对照，本身不花钱**。真正的差别在超出免费额度之后：Basic **0.15** 元/次、高精度 **0.50** 元/次（贵 3 倍多），以及精度 96% vs 99%。**所以先用 Basic 跑一批看效果**，用数字决定要不要长期走高精度。

**★ 结论修正（推翻了上一轮「高精度更准」的判断）**：这**不是精度高低**的问题，而是**两个引擎的切分策略不同**。同一句话，Basic 常切成 `…知书达`、高精度切成 `…知书达礼`；菜单那张 Basic 切出 259 行、高精度合并成 148 行。对 `instr` 字面搜索来说，**行边界不同 = 命中与否不同** —— 搜「知书达礼」时，只有高精度那半给得出完整四字。

⇒ **「两个都跑、结果合并」不是「多一份保险」，而是把召回从 464 / 340 行抬到 650 行的实质提升**。代价是每张 2 次调用（全库 61 张 = 122 次，之后每月新增几十张 ≈ 100 次），**始终落在 2000 次/月免费内**。

**幻觉的实测频度**：12 张里只出现 1 次（那张水果碗）⇒ 过滤规则仍要做，但它不是高频问题。

**一条被实测否掉的路线**：**「分级」（Basic 先跑、没认到字才上高精度）不可行** —— 样本里 Basic **认到了字、却漏了 `STARBUCKS`**，它不会报 `ImageNoText`，于是永远不触发升级，品牌词照样丢。

**为什么「把多个免费接口都用起来」只能落到 2 个**：只有 `GeneralBasicOCR` 与 `GeneralAccurateOCR` 是**同一个任务的两个档位**（「照片里有什么字」）。其余免费接口各管一件事 —— 表格识别返回行列结构、二维码识别返回码内容、印章 / 身份证 / 名片 / 运单识别返回各自字段 —— 拿它们去读书页或菜单**不会给出想要的结果**。

## 11. 降级链：高精度 → Basic →（本地 tesseract 预留）（2026-10-16 蛋妞拍板：**先做前两级，已完成**）

### 11.1 要的效果

- 首选 **高精度**（品牌 / 日期 / 小字最准）
- 高精度额度用完 → **自动**换 **Basic**（不用人工改配置、不用重启）
- Basic 也用完 → **本轮停手**，不要一张一张白试
- 第三级**本地 tesseract**：接口缝留着（`PhotoTextRecognizer`），**本轮不做** ——
  蛋妞目前没在本机 / 服务器放本地 OCR，且 4C4G 上跑识别会跟别的项目抢 CPU；等真需要了再接。

**这与「两个都跑」是两条路，要分清楚**：两个都跑 = 每张调 2 次、覆盖率 100%；
降级链 = 每张只调 1 次，但**用的那一档是当下能拿到的最好的**。蛋妞选的是后者。

### 11.2 什么错误才算「这一档不能用了」（必须精确）

实现见 `apps/api/src/photo-text-chain.ts` 的 `classifyOcrFailure`，三分法：**换档 / 停手 / 只跳过这一张**。

| 腾讯云错误码 | 含义 | 动作 | 计费（官方表） |
| --- | --- | --- | --- |
| `ResourceUnavailable.ResourcePackageRunOut` | 该 action 的资源包耗尽 | **换下一档** | 否 |
| `ResourceUnavailable.InArrears` | 账号欠费 | **换下一档**（下一档未必欠费） | 否 |
| `FailedOperation.UnOpenError` | 该接口未开通 | **换下一档**（开通是按接口算的） | 否 |
| `AuthFailure.*`（签名 / SecretId / 鉴权） | 密钥错或没权限 | **停手**（换档也没用，共用一个密钥） | 否 |
| `InvalidParameter*` / `InvalidParameterValue*` / `InvalidAction` | 请求或 action 名有问题 | **停手**（配置错，逐张试只是白跑） | 否 |
| `FailedOperation.ImageNoText` | **照片里就是没字** | **正常结果**（返回 null），**不换档** | **否** |
| `RequestLimitExceeded`（限频，>20 次/秒） | 抖动 | **不换档**，跳过这张（下轮会补） | 否 |
| 网络错 / 超时 / 响应非 JSON | 抖动 | **不换档**，跳过这张 | 否 |

> **为什么「不换档」这一列这么重要**：一次网络抖动就把整库切到 Basic，等于**永久降级**
> （已跑过的照片不会重跑）。**只有服务明确说「这一档不能用了」，才换。**
>
> **停手为什么要带冷却**：`AuthFailure` 这类是配置问题；若永久停手，密钥改好后还得重启进程。
> 所以实现里「停手」只是休整 **5 分钟**，到点自动回头试首选档（修好了就自愈）。两档都用尽时同理。

### 11.3 换档状态存哪：内存 + 到期时间

- 进程内存里记「当前档 / 为什么换 / 什么时候该复位」
- **复位点 = 下个月 1 号 00:00（Asia/Shanghai）** —— 额度是每月 1 号发的，到点自动回到高精度

## 12. 怎么把成本压下来（2026-10-16 实测后定稿）

### 12.1 先算账：现在的真实成本是 0

| 项 | 数 |
| --- | --- |
| 全库去重照片 | 60 张 |
| 每档免费额度 | 1000 次/月（各自独立，每月 1 号发、当月清零不结转） |
| 两个云端档全库跑一遍 | 120 次 = 各占 **12%** |
| 月新增（按几十张估） | ≈ 100 次/月 |

结论：**在免费额度内，OCR 的成本是 0**。任何「省额度」的优化，省的都是**还没花的额度**。

### 12.2 「没字的图不发请求」—— 实测结果和直觉相反

拿一张确定无字的照片（AI 描述里一个文字线索都没有），两个引擎各调一次：

| 引擎 | 服务返回 | 官方计费表 | 实际 |
| --- | --- | --- | --- |
| `GeneralBasicOCR` | `FailedOperation.ImageNoText`（Error 对象） | **不计费** | 不花额度 |
| `GeneralAccurateOCR` | **成功 + 1 条文本 `.`** | 成功即计费 | **花了 1 次** |

（可回查：Basic `b4474624-8d71-431a-b021-27223d303344`、高精度 `51fc0260-db2e-44b6-91aa-7f3668b4e090`。）

两条结论：

1. **Basic 遇到无字图根本不扣额度** —— 服务明确返回「未检测到文本」，而这个错误码在官方计费表里是「否」。
   所以对 Basic 而言，「提前拦截无字图」**一分钱都省不到**，只省一次网络往返。
2. **高精度会把无字图当成一次成功调用**（还返回了一个幻觉出来的 `.`）⇒ **计费**。
   ★ 这一条**更正** §9 里我写的「10 张里复现不了幻觉」：**幻觉是真的，只是偶发**。

### 12.3 那要不要做「提前拦截」？—— 不做

1. **收益上限极小**：全库 60 张里，「描述完全不含文字线索」的 19 张（31.7%）。但**这 19 张里明显有字的不少** ——
   样本里就有「游戏结算画面显示"战败"，三队进度条分别为 100、92、57，下方列出"第三名 + 贡献 $16,200"」。
   ⇒ **「描述里没有文字线索」≠「图里没有字」**，这个免费判据本身就不可靠。真正能省的只占额度**零点几个百分点**。
2. **代价是不可逆的漏识**：预判「没字」⇒ 不发请求 ⇒ 那张图**永远搜不到**。而 OCR 存在的理由正是**AI 描述漏看的那些字**。
3. **没有免费的可靠判据**：本地像素启发式（边缘 / 连通块）理论免费，但准确率未知、要调参、要人工标注一组样本去验证它 ——
   为省 0.x% 的额度做这件事，不值得。

### 12.5 别让「无字」的照片被反复查 —— ✅ 2026-10-16 已完成

**问题**：`collectKnownDescriptions` 只认「有文本」的条目。无字照片不落库 ⇒ 它**永远留在待办里** ⇒
**每点一次识别，它就被重新调用一次**，而且永远 `described = 0`。在高精度档，每次都是一次**计费**调用。
一旦库里有字的照片都跑完，之后每次点按钮就是 **100% 白调**。

**做法**：text pass 对「服务明确回答没有字」的照片落一条 `text: ""` 的 `photo-ocr` 条目
（含义 = 「查过了，这张图没有字」）。搜索是子串匹配，空文本不会命中任何词，所以对搜索**零影响**。

**但落标记之前，必须先解决一件事：把「没字」和「没问成」分开。**

改造前识别器返回 `{text, engine} | null`，而 `null` 同时表示「图里没有字」和「网络抖了 / 额度没了 /
没配凭证」。**在这个返回值上直接落标记，等于把一次网络抖动写成永久事实** —— 标记一旦落下去，
那张图以后就不问了。所以返回值升级成三态：

| 返回 | 含义 | 落库吗 |
| --- | --- | --- |
| `{kind:"text", text, engine}` | 读到了字 | 落条目 |
| `{kind:"blank", engine}` | **问了，这张图里没有字** | **落空标记** |
| `{kind:"unread"}` | 没问成（抖动 / 限频 / 额度尽 / 没配凭证 / 图读不出来） | **什么都不落**，下一轮自然重来 |

实现细节（每一条都是「不这么做就会坏」）：

- **没配凭证 ⇒ 一律 `unread`，绝不 `blank`**。否则第一次跑就会把**整库**标记成「没有字」，且永久跳过。
- **描述档（caption）不参与**：模型答 `NONE` 仍不落库 —— 「模型说不出」≠「这张图没有字」，只有后者值得记。
- **空标记也记 `model`**（哪一档确认它没有字），将来想按引擎筛是查得到的。
- **`force` 能覆盖空标记**：换引擎后可以把「已标记无字」的照片重问一遍。
- **换图安全**：`sourceRevision` 就是内容哈希，换了文件即新 key，会重新识别。
- **不进 `samples`**：样本是「读出来的话」，空标记没话可说；但它照旧写进记录。
- **报告新增 `unread` 字段**：让「这一轮其实什么都没读成」看得见，而不是看起来像「库里没有字」。

**一个必须说准的边界**：对 `GeneralBasicOCR`，无字图返回的是 `ImageNoText` ⇒ `blank` ⇒ 落空标记；
但 §12.2 实测过**高精度档会把无字图当成一次成功调用**（返回一个幻觉的 `.`）⇒ 落的是文本条目而不是空标记。
两者**都**算「这张问过了」，所以「不再反复查」的效果一致；差别只是高精度档会留下一个 `.`。

**后果**：库里会多出一批空文本条目。将来界面要展示「这张照片认出了什么」时，
空条目应显示「没有文字」，而不是一个空白块。

**验证**：`apps/api/test/photo-description.test.ts` 新增 6 条（空标记落库并被下轮跳过、空标记不命中任何搜索词、
没问成不落库且下轮重问、没配凭证绝不标白、描述档仍不落库、`force` 能覆盖空标记）；
`photo-text-chain.test.ts` 全线改成三态断言，其中「限频只能回 `unread`、绝不能回 `blank`」单列一条。
