# 三轮递进式 Debug 提示词（LifeOS 专用，只诊断不修复）

> 用法：新开一个会话，把下面 `---` 之间的内容整段贴进去。它自带停止条件与交付格式，
> 不需要你再补充上下文。
> 维护：本项目新增「踩坑类别」时，把它追加到第 1 轮的**模式库**里 —— 那是这份提示词的弹药。

---

## 你的任务

对 `E:\Projects\motion-lab\lifeos` 做**恰好三轮**递进式 Debug 审计。每轮把已确认或高度可疑的缺陷
从「实例」提炼为「根因类别」，下一轮必须先执行这些类别的定向搜索，再扩大到相邻模块、相同数据流和反向边界。
第三轮结束后写一份**可独立阅读的详细 Markdown 报告**，然后停止；**不要修任何 Bug**。

只允许写审计报告、必要的隔离诊断产物，以及按 `AGENTS.md` 要求最小追加 `docs/todo.md` / `docs/changelog.md` 交接记录。
不要改源码、测试、配置、数据库、资产、现有验收脚本或部署文件；不要提交或推送。

## 环境铁律（本项目专属，违反会浪费整轮）

- **Node 用 `C:\Program Files\nodejs`（24.x）**；如需直接调用 npm CLI，用
  `C:\Program Files\nodejs\node_modules\npm\bin\npm-cli.js`，避免 PATH 内旧版 Node 混入。
- **bash 是残缺 PortableGit**：优先用 `rg`、PowerShell 原生命令或内置工具；不要依赖 `ls/cat/grep/find`。
- **不要杀任何现存端口进程**，尤其 3001、3011、5199。3011/5199 连的是主人生产 `data/`；
  不要对它们发写请求。只读请求也应先说明目的并确认目标，能用隔离实例就用隔离实例。
- **禁止** `git push`、`git commit`、`git checkout .`、`git stash`、`git reset --hard`、`git clean -fd`。
  本任务无代码修复，不需要 Git 检查点。
- **不要生成截图、不要在回复里贴图** —— 主人自己开 `http://127.0.0.1:5199/` 看。
- 不要动 `data/`、`.env`、`pic-test/`、`deepseek-v1/`、`deepseek-v2/`、`.workbuddy-ai/`。

## 三轮怎么递进（这是本任务的核心机制）

每一轮都必须产出**三类东西**：

- **A. 实例**：`文件:行` + 症状 + 可复现证据（命令/断言/数字）
- **B. 类别**：一句话命名的**根因模式**，附上具体的 `rg` 正则 / 断言模板 / 只读复现命令
- **C. 下一轮搜索卡**：来源问题编号、要搜的路径和搜索式、预计同族变体、应排除的正常用法、验证步骤

**下一轮的开场动作 = 逐张执行上一轮搜索卡**，把一个实例扩成全仓同类实例；每张卡都要报告
`命中数 → 人工审查数 → 已确认数 → 排除数`。不能因为预设搜索轴更方便就跳过上一轮发现。
对同一根因，沿 `入口 → 校验 → 持久化 → 读取 → UI → 导出/备份/后台任务 → 测试/部署` 追踪；
对同一接口，反查「未认证、另一租户、禁用账号、旧会话、错误配置、重启后」等对抗状态。
第 3 轮新归纳的类别只写进最终报告的「后续验证建议」，**不启动第 4 轮**。
三轮都必须执行，即使某轮零新发现，也要在下一轮扩大搜索式并记录零命中的证据，不能提前停。

### 第 1 轮 · 模式库扫捕（已知坑的同类实例）

按下面这份**本项目真实踩过的坑**当模式库，逐条全仓搜同类实例。
不要只报「已经写在 changelog 里的那一个」，要找**还没被发现的同族**。

1. **时间与日期**
   - 按天分桶是否用了 UTC `slice(0,10)` 而不是
     `new Intl.DateTimeFormat("en-CA", { timeZone: "Asia/Shanghai" }).format(...)`（跨午夜会归错天）
   - `from/to` 范围查询是否按 UTC instant 分组，导致跨午夜记录落到相邻日期
   - 42 格月历第一格是否被当成 1 号（正确 = 包含 1 号那周的周一）
   - 未来时间封顶：`isFutureDay` / `minuteCapFor` 的边界（按 hour 比较，不是按当前时刻）
   - 验收脚本/夹具里是否**硬编码了具体日期**（会在午夜静默失效，失败形态像产品回归）
2. **CSS 布局与动画**
   - `animation-fill-mode` 默认 `none`：**正 `animation-delay` 期间元素按基准样式渲染** →
     任何「从屏幕外飞入」的元素，基准位置本身必须在屏幕外
   - `height: auto` 不可插值：`auto → 0` 直接设会瞬移，必须先钉住像素高度并**强制回流**
   - 同优先级 class 覆盖：后写的规则会赢（`.kind-switcher` 自带 margin 顶掉过 `.review-composer-kinds`）
   - `transform` 不改变布局盒宽 → 用 `translateX` 叠压会溢出容器，而 `documentElement`
     的横向溢出可能是 0，**光看页面级溢出会漏掉泄漏**
   - 旋转/变换后画出来比布局盒宽（`w·|cos| + h·|sin|`）
   - `prefers-reduced-motion` 下：0.01ms 动画会停在**最后一帧** → 每个动画图层都要有显式静止态
   - 动画属性白名单：只许 `transform` / `opacity`；动 `filter` / `background-position` /
     `box-shadow` / `width` / `height` 都是逐帧重绘
   - `backdrop-filter` 压在逐帧动画层上 = 每帧回读背景
   - **细周期图案 + 快速平移 = 摩尔纹**（10px 条纹 @ 226px/s 就是 22.6 周期/秒）。
     「数学上无缝」只解决接缝，不解决 aliasing
   - 基础 class 的规则不受修饰 class 作用域限制（`.fog-line` 曾被 `.weather-bg--foggy` 漏掉）
   - 内联 `!important` 会打死任何选择器（`MentionBox` 给 textarea 写了
     `min-height: 0px !important`，CSS 里的 `min-height` 全是死代码）
3. **状态与并发**
   - 乐观锁：任何「先建后改」的脚本，改写成功后必须**用返回体刷新本地缓存的 revision**
   - 弹窗外侧点击关闭是否只看 `click.target === dialog`？输入框内按下、拖出弹窗松手也可能把合成 click 归到 dialog，导致草稿误关；须按同一 pointer 的按下/松开起点和终点判断，并验未保存草稿、Escape、快速关后重开。原生 `close` 事件可能在新弹窗打开后才到，不能重复改父状态。
   - React 批处理：同一事件里两次 `setState` 会进同一帧 → 依赖「中间必须有一次绘制」的动画会退化成硬切
   - 请求竞态：切日期/切筛选时旧请求后到会不会覆盖新状态（`AbortController` / 请求序号）
   - stale closure：`useCallback` / `useEffect` 依赖是否漏项
   - 缓存键是否够唯一（`snapshotCache` 键缺 `targetDate` 是已知遗留）
   - 乐观更新失败后是否回滚
4. **验收基建自身**（最容易骗人，优先审）
   - 断言是不是在测「DOM 存在」而不是「视觉可见」（`display:none` / `visibility:hidden` /
     `height:0` 的元素仍在 DOM 里，会命中隐藏元素）
   - **瞬态缺陷**是否只比了「前后」而漏掉「过程中」（滚动条出现/消失、过渡抖动、乐观更新回滚）
   - 脚本崩溃时会不会留下上一次的 `RESULT: PASS`（只代表「没跑到失败那一步」）
   - 缺省端口是否对（`verify-privacy` / `verify-smart-mentions` 缺省 3012，不是 3011）
   - 陈旧脚本（`verify-places.mjs` 找的 `.place-toggle` 在 HEAD 已不存在）
   - 量像素/量几何前是否排除了无关干扰（整卡量文字边缘会让高频能量基线失效）
5. **安全闸门与批量清理**（闸门失效比没闸门更危险——它给人「已经受保护」的错觉）
   - 判定用的字段是否真的指向目标？`/api/backup/status` 的 `localDirectory` 是
     **可独立配置的备份目标**，不是实际数据目录；即使改成「包含」也不能证明安全。
     须核对有效 `dataDirectory`、`databasePath`、`assetRoot`，并防止 DB/资产单独指回生产路径
   - 闸门是否 **fail-closed**：目标应答了但报不出数据目录时，必须**当生产处理**，
     不能「未知所以放行」
   - 闸门是否相信了**它验证不了的线索**（环境变量 / argv / 配置文件声称「目标是隔离实例」）？
     正解：线索必须**双向佐证** —— ① 该端口真应答且报告可验证的隔离 DB/资产有效路径；
     ② **入口脚本自己的源码里真的读了这个变量**（剥掉注释和字符串字面量再检查，
     否则只在说明文字里提到变量名就能骗过它）。
     任一条不成立 → 拒绝，并打印**为什么忽略了这个变量**（静默拒绝会让人以为是别的问题）
   - 有没有**唯一豁免口**？没有 → 那唯一合法的用例会永远报红 → 所有人学会忽略这个检查。
     豁免要显式、要能署名（本项目的 `@unguarded-on-purpose` 标记）
   - 闸门有没有**双向回归测试**（既测拦住、也测放行）？只测拦住的话，
     一个「永远拒绝」的坏闸门会通过测试
   - 测试脚手架本身：**`spawnSync` 会阻塞父进程事件循环** → 父进程内的假服务器永远答不上，
     所有断言会**因为错误的原因失败**（看起来像被测代码坏了）。异步 `spawn` + Promise
   - 批量清理/删除脚本是否遵循「**有一条认不出就整体中止**」？
     把「我认不出这条」读成「这条是垃圾」是最贵的一类误删（本项目 `purge-trash-junk.mjs`
     要求全部 105 条都命中已知签名，否则不删任何一条）
   - 清理脚本删完是否**断言「主人能看到的东西一条没变」**（活记录数、按人写入数）？
6. **账户登录、多租户与部署边界（2026-09-24 新增）**
   - `server.ts` 外层账户网关是否覆盖**全部** `/api/*`，包括健康、未知路由、资产原件、导出/导入、
     备份/时光机；旧共享密码入口、URL、header、cookie 中的自报 tenantId 能否绕过身份路由
   - owner 建号、停用、改密后旧会话是否马上失效；普通成员能否调用管理 API；登录失败限流能否
     通过换用户名/IP、超长用户名或大量失败桶绕过或耗尽内存
   - `tenantConfigFor` 是否覆盖 DB、资产、缩略图、快照、本地备份、定时任务、四类加密密钥及
     S3 前缀；是否有模块偷偷读根 `process.env` 或 owner 的绝对路径；符号链接/路径穿越能否逃出空间
   - 同一浏览器 A→登出→B、A 被停用→B 时，React 缓存、请求竞态、localStorage 聊天/草稿、
     下载链接是否仍显示 A 的内容；首屏身份尚未解析时是否闪现旧空间
   - 配置文件、`.env.example`、`compose.yaml` 与 README 是否一致；Compose 显式环境映射是否漏传
     `LIFEOS_*_CONFIG_SECRET`，移除引导密码或迁移数据目录后密文能否解开；端口是否只绑定回环、
     HTTPS Origin 与 Secure Cookie 是否 fail-closed。**不要连接真实域名或服务器做破坏性测试**

### 第 2 轮 · 按轴扩张（同类但形态不同）

第 1 轮找的是「同一个坑的同类实例」。第 2 轮换成**四条轴**，每轴找**形态不同但根因同族**的问题：

- **轴 A · 时间**：所有「按天/按周/按月/按时段」的代码路径，逐个对表时区与边界（含 DST 无关性、
  月初月末、闰年、23:55 归档、整点观测、30 分钟刷新窗口）
- **轴 B · 布局与渲染**：所有 `position: absolute/fixed`、所有 `overflow`、所有 `grid/flex`
  的溢出与裁剪、所有动画元素、所有响应式断点（尤其 ≤720 / ≤560 / ≤390）
- **轴 C · 状态与契约**：core 的模型/校验 ↔ api 的读写 ↔ web 的类型与渲染，三处字段是否一致；
  隐私字段（`isPrivate`）在时间轴/导出/日历摘要/预览里是否都被正确过滤；`revision` 在每条
  写路径上是否都参与乐观锁
- **轴 D · 失败路径**：网络失败、401、409、413、超时、空数据、超长文本、超量照片、
  上传中断、S3/本地伪桶切换、AI 无 key 回退 —— 每条失败路径是否都有可读的反馈且不丢用户草稿
- **轴 E · 身份与资源归属**：以 owner、成员 A、成员 B、禁用成员、未登录五种身份，逐项追踪
  records/entities/assets/content、搜索/摘要、导出/导入、配置、备份/时光机和后台任务；
  查「列表隔离了但按 ID 直取没隔离」「API 隔离了但浏览器缓存没隔离」这类不同形态的同族缺陷
- **轴 F · 部署契约**：`readConfig` ↔ Compose 环境映射 ↔ README 示例 ↔ 容器持久卷/反代 Host/Origin，
  查启动时、重启后、去掉 owner 引导密码后是否仍保持安全与密钥可解；仅静态审查本机配置，不连服务器

### 第 3 轮 · 跨层与边界（把战果扩到契约层）

- **导出/导入往返**：JSON 与 Markdown 导出后再导入，字段是否无损（含天气附件、关联、
  隐私标记、`isDemo`、`assetRefs`、`revision`）
- **空与极值**：0 条记录、1 条、9 张照片、10 张、超长单行、纯 emoji、纯空白、
  同名实体、删除后仍被引用
- **预算回归**：天气每形态 ≤ 20 节点、动画属性白名单、`filter` 只允许出现在
  `cloud--far` / `fog-band` / `lightning-bolt`、`.weather-header *` 里 `backdrop-filter` = 0
- **可访问性**：可点击但不可聚焦、可聚焦但不可见、`aria-label` 与可见文案不符、
  键盘无法到达的交互
- **性能**：是否有每帧重排/重绘、是否新增了未命中缓存的请求、缩略图是否复用同一 URL
- **多租户变形测试**：同一组操作交换 A/B 身份或伪造另一租户 ID 后，返回内容必须只由服务端
  会话决定；对同一资源依次尝试列表、按 ID 获取、修改、删除、下载、导出、备份快照读取，
  不得只测其中一个入口。只在隔离数据目录里做，不借用主人账号或真实数据
- **跨重启与配置变更**：隔离实例里验证禁用/改密后的旧会话、四种集成密钥和备份前缀在重启后
  保持正确；发现问题只记录复现，不修改实现或“顺手调整配置”掩盖问题
- **逆向检查测试本身**：每个声称覆盖隔离/安全的测试，确认断言对一个故意错误的结果会失败；
  检查 CDP `returnByValue` 是否把 DOM 节点误当布尔、Origin 是否只在测试层伪造而不能代表生产代理、
  `RESULT: PASS` 是否来自本次运行而非旧文件

## 每轮记录与证据标准

在同一份工作笔记中维护问题编号（如 `R1-01`、`R2-03`），到第三轮整理为最终报告。
每轮至少记录以下四栏：

1. **执行日志**：搜索式、搜索范围、命中数、审查数、确认数、排除数；上一轮每张搜索卡的去向。
2. **问题实例**：`文件:行`、入口条件、预期/实际、根因假设、严重度、证据命令与关键输出。
3. **举一反三**：该问题还可能在哪些入口/数据流/身份/状态复现，下一轮的具体 `rg` 式和只读验证法。
4. **排除与盲区**：误报为何不成立，哪段代码/哪个运行条件尚未验证，避免下一轮重复猜测。

严重度：**P0** 可造成跨租户泄漏、未授权访问、实质数据丢失或可直接利用的高危安全问题；
**P1** 核心功能错误、可靠复现的错误状态或恢复失败；**P2** 局部交互/视觉/次要功能错误；
**P3** 有明确后果的维护或测试缺口。不要因为代码看起来危险就自动标 P0。
证据状态只能是 **已复现 / 静态证实 / 疑似待验证 / 环境受阻**；
“测试通过”不等于“没有 Bug”，“未复现”不等于“已排除”。

## 第三轮结束后只生成一份详细报告

写入 `docs/debug-audit-report-YYYY-MM-DD.md`（日期用本地 `Asia/Shanghai`），最终回复给出这个文件的**绝对路径**。
报告至少有以下内容：

1. **执行摘要**：审计时的提交号、工作树原有改动、覆盖范围、P0/P1/P2/P3 数量、最优先处理的 3 项；
   明确写「本轮只诊断，未修复、未提交、未推送」。
2. **基线与环境**：Node 版本、typecheck/test 命令及结果、隔离数据目录、哪些检查因环境或安全边界未跑；
   说明没有触碰主人 `data/`、3011/5199 或真实服务器，若做不到则如实说明。
3. **三轮递进链**：按 `第 1 轮发现 → 第 2 轮搜索式/命中与新变体 → 第 3 轮跨层验证/最终结论`
   列出每个根因类别。零发现的轮次也列执行过的搜索，不许空白跳过。
4. **问题总表**：`ID | 严重度 | 证据状态 | 问题 | 首次发现轮次 | 影响范围 | 文件:行`；
   同根因多个实例合并一个主问题并列出所有受影响位置，避免重复计数。
5. **逐项详情**：预期/实际、触发前提、最短**安全**复现步骤、关键证据（命令和节选输出）、
   从入口到后果的根因链、受影响与不受影响的路径、建议修复方向及建议回归测试。
   建议只能写在报告里，**不得照建议动手修改**。
6. **未证实与已排除**：每条疑似项的下一步验证条件；每条高相似误报的排除证据；
   生产域名、证书、宝塔和真实备份恢复如未接触，要单列为「未验证」，不得写成已通过。
7. **交接顺序**：按风险和依赖给后续修复者排序，但不实施；标注需要主人决策或生产权限的项。

报告每条确定性结论必须能追到具体文件行和可复核证据。脚本日志只引用必要片段，
不抄录密码、Cookie、API Key、主人记录正文或照片路径中的私人信息。
若项目规则要求未完成事项入 `docs/todo.md`、文档变更入 `docs/changelog.md`，按 `AGENTS.md`
做最小追加并附报告链接；**这些交接性文档更新不是修 Bug 的授权**。

## 停止条件与最终回复

**无论发现多少问题或某轮零发现，都做满三轮；**第三轮报告完整落盘后立即停止。
若发现可能正在造成生产数据损害的 P0，先用非破坏性方式提醒主人，再继续安全审计；
需要额外权限或危险复现的部分标「未验证」，不要冒险操作。

最终回复只概括三轮覆盖范围、各严重度数量、最重要的发现和未验证边界，
并提供 `docs/debug-audit-report-YYYY-MM-DD.md` 的绝对路径。不修 Bug、不提交、不推送，
也不要把「修复建议」误写成「已修复」。

## 绝对不许做的事

- 修改产品源码、测试断言、配置、数据库、资产、部署文件或已有验收脚本
- 在生产 `data/`、3011/5199、真实域名或服务器上造数据、跑写入验收、删改或恢复
- 因为基线红/某轮零发现而少做一轮，或为了凑数把疑似项写成已确认 P0/P1
- 只重复 `changelog` 里的旧坑，不在下一轮按根因扩大搜索
- 用 `git reset --hard`、`checkout .`、`stash`、`clean -fd` 清场；生成截图；泄露密钥或私人记录
- 为了让断言变绿而改断言，或在报告外偷偷实施修复
