# LifeOS 平滑接入弹指存储池

第一阶段已在本地实现并验收：日常继续使用原存储，后台向弹指池复制本地原件和加密业务快照，每件上传后读回校验。复制不会替换现有资产引用、删除旧文件或撤掉旧备份。线上复制尚未执行。

## 两个项目如何衔接

本地弹指项目位于 `D:\apps\go`。LifeOS 的 Node API 通过本机 PHP CLI 调用 `apps/api/php/pool-consumer-worker.php`，worker 调用弹指现有 `PoolConsumer`。消费方沿用面板已经登记的 ID `2`；不得删除、重建该 ID。

一个文件只上传到池中的一个后端，不新增双副本。桶选择由弹指 `storage.php` 负责，LifeOS 保存返回的不可变对象 key。新增账号/桶在弹指管理界面配置；既有对象保留原 key 和前缀，不因加入新桶而搬迁。项目和用户额度仍须分配：加入桶不会自动提高项目 `2` 已分配的额度，也不会改写旧对象所在桶。

弹指本地 `58cdb06` 支持已登记的数字项目 ID，`e51d05e` 让下载返回实际扣费的 UTC 月份。2026-10-07 核对时两项已在本地源码中，Go working tree 干净；服务器版本未知。LifeOS 本轮没有修改 Go 文件、其真实配置或共享账本。

## 第一阶段的行为

| 项目 | 当前行为 |
| --- | --- |
| 现有记录、照片、资产引用 | 保留，继续从原位置读取 |
| 新照片上传、完整包导入的原件 | 过渡模式下继续保存到本地原存储 |
| 后台复制 | 可指定账号范围；未指定过范围时处理已登记 owner 和成员，包含禁用成员的既有数据库及可恢复回收站原件 |
| 数据库副本 | 只导出业务表，包含私密内容、软删记录、手写小结、周期与天气数据；AES-256-GCM 加密后上传 |
| 快照频率 | 每空间最多每24小时生成一份；内容指纹未变则不重复生成 |
| 图片等原件副本 | 按原始字节复制；这是原件镜像，不是密码加密导出包 |
| 校验 | 上传后经 PoolConsumer 读回，比对大小与 SHA-256；失败不算已验证 |
| 校验失败重试 | 已有对象 key 时只重试读回，不重复上传 |
| 上传结果不明 | 保留待核对状态和额度预留；重试按钮不重复 PUT、不自动释放额度 |
| 暂停、重启 | 后台暂停后日常仍使用原存储，模式持久化；开启中的队列会在重启后继续处理 |
| 自动原件 GC | 过渡模式中暂停，防止自动回收旧原件；用户主动编辑/删除仍遵守既有功能规则 |
| 旧备份、旧 S3 设置 | 保留；本轮没有改写自动 SQLite 备份的目的地 |

每次最多处理20项，剩余工作由下一次唤醒处理；运行中每60秒扫描，上传成功也会唤醒扫描。旧版本、失败和待核对项均保留在私有队列中，当前数字是任务/版本数，不是撤旧条件。没有自动清理远程版本、保留期管理、切换读取或撤旧按钮。池中既有 `lifeos-pool` 引用沿用原授权读取，不再次上传；其他外部引用报告为需核对，不猜测归属。

## 上传部署时的顺序

两边本地代码可以按现有发布流程分别更新到服务器；无需提供服务器登录凭据才能准备接入。服务器实际使用哪个用户、PHP CLI 权限及两边是否同机，仍需在上传后按 [同机接入核对](storage-pool-deployment.md) 验证。本轮未提交、未推送、未远程更新。

1. 保留现有数据库、原件、身份库、配置密钥及独立整站备份。不要改数据目录或既有 `LIFEOS_*_CONFIG_SECRET`。
2. 先更新弹指接入层和 LifeOS 源码，确认项目 `2` 仍存在且额度有效。以服务运行用户核对 PHP `curl`、`pdo_sqlite`、私有配置/账本权限、`open_basedir` 和系统临时目录。确认池后端的访问策略能保护用户原件，不能假设所有免费桶都是私有桶。
3. 服务器私有 `.env` 同时配置下面两个开关，并使用真实 PHP CLI 路径。第一次重启就保护本地写入，后台复制仍保持未开启：

   ```dotenv
   LIFEOS_STORAGE_POOL_ENABLED=1
   LIFEOS_POOL_LOCAL_PRIMARY=1
   LIFEOS_POOL_CONSUMER=2
   LIFEOS_POOL_PHP_BINARY=/实际/php/cli
   LIFEOS_POOL_WORKER_PATH=/www/server/lifeos-app/apps/api/php/pool-consumer-worker.php
   ```

   需要既有账户模式；不要为接入池而重建身份库。删除 `LIFEOS_POOL_LOCAL_PRIMARY` 或点击暂停都不会自动切回池写入。尚未进入过渡的新空实例可以继续使用原有直接上传池的模式。
4. 对服务器的实际数据路径运行只读清单。输出父目录须已存在且在数据/资产目录之外；输出文件必须是新文件：

   ```sh
   node scripts/storage-pool-inventory.mjs --data-dir /实际/data --asset-root /实际/assets --out /私有盘点目录/pool-before.json
   ```

   数据库另有路径时加 `--db-path`。它只读文件和业务库，不联网、不迁移；缺文件、大小/哈希不符、路径越界、孤儿文件及账号无法归属会显式报告。退出2表示盘点不完整，不能把它当作迁移成功。
5. owner 登录「设置 → 账户 → 当前会话」（`#settings/account/session`），核对实时项目容量/流量并分配用户额度。旧归属不完整、未决账目仍由原有守卫阻止额度调整，不绕过；先处理具体问题。正常可读文件可以分批复制，未完成项目不能据此撤旧。
6. 点击「开始双轨复制」。连接核实失败返回503，后台不开启，日常本地上传仍可用。查看已验证大小、失败、待核对项目，按需暂停或重试。读回校验会消耗项目与用户的月流量；先按实际流量余量安排批次。

弹指新增桶后还须检查项目 `2` 的分配额度和每个后端剩余空间/流量。单文件必须能放进一个后端，容量相加不意味着大文件会自动拆分。

## 本地真实数据测试与统一账本

主人已选择先接通云端统一账本，再把独立测试账号纳入现有 LifeOS 项目 `2`。不另建测试消费方，不在本地创建共享账本副本，也不把本地私有配置覆盖到服务器。

2026-10-07 已准备一致性业务库副本与独立账号 `lifeos_local_test`，目录为 `.review/real-data-migration-jyKclJ`。其中262份原件共367,870,037字节（约351MiB），166条记录（含12条软删）、81份当前资产和182份可恢复回收站资产。新身份、账号ID、租户ID和主密钥均独立；原身份、集成密钥和配置没有复制。`holiday.jpg` 仍缺失，保留其元数据，不能将此次测试宣称为全部原件恢复成功。副本固定在准备时刻，运行中的原应用后来更新了天气缓存，记录等其他业务表仍一致。

本地三个真实桶的签名只读列举请求均返回 HTTP 200，但本地 Go 配置仅登记 `default`，没有项目 `2` 或统一共享账本。因此桶密钥能访问文件不代表能正确更新服务器上的项目圆环。服务器检查步骤见 [同机接入核对](storage-pool-deployment.md#统一账本检查工具)。本次尚未上传真实用户文件，原存储保留。

统一账本确认后，在云端现有身份库建立独立测试成员并确认目标空间为空；本地准备账号是隔离实例的 owner，不直接复制其 `identity.sqlite` 覆盖云端身份库。通过既有完整加密包导入流程或经审核的空间搬入流程把业务副本和原件交给该成员，服务端账号ID以云端注册结果为准；用户名不同只用于登录，不能代替账号ID绑定。因已知缺件，完整包导出会明确拒绝，不能绕过其完整性校验；复制测试可保留缺件报告，只上传确实存在的原件。

开始复制时，由 owner 对 `/api/admin/storage-pool/transition` 发起指定范围的请求：

```json
{"action":"start","accountIds":["云端独立测试成员的真实账号ID"]}
```

`accountIds` 必须是非空、唯一的已登记账号ID数组（最多1000个），仅 `start` 接受此字段。暂停、重启和只发送 `{"action":"start"}` 均保留既有范围，界面会显示指定账号数量；扫描、重试、进度和失败列表都按该范围处理。只有 owner 显式发送 `accountIds:null` 才恢复全账号范围，测试阶段不要发送。更改范围或暂停时当前在途操作完成，下一项按新范围执行；先等当前任务结束再切换测试对象。

复制仍按项目 `2` 的统一账本及逐用户额度计量。至少为约351MiB原件、加密业务快照及其读回流量留出余量；真实读取和重试也消耗流量，不把静态桶额度当作实际剩余。服务端同机权限、原件访问策略和测试用户归属须先确认，再开启复制。

## 加密与恢复边界

业务快照格式 `lifeos-pool-space-v1` 使用服务器身份库中的稳定主密钥按账号派生加密 key。服务器仍能读自己的业务数据；没有对应主密钥就无法恢复快照。快照不包含账号、会话、API key、存储账本或调度配置。

复制映射在 `dataDirectory/pool-transition/jobs.sqlite`，用户用量和对象归属在 owner 数据库，弹指共享账本继续保留在其原私有路径。恢复照片副本需要对应映射；不能只下载一个业务快照就宣称整站可恢复。服务器整体恢复还须保存 `identity.sqlite`、原配置、owner 数据库和复制队列；现有整站备份继续使用，并需单独核对是否包含新增队列目录。自动生成的加密暂存文件也在 `pool-transition/`，本阶段不自动回收。

按需生成并下载的密码加密完整包仍是独立的 `.lifeos` 格式，见 [完整包协议](archive-format.md)：它包含原件，使用导出时的密码，不长期占用对象存储。不要把该包与服务器业务快照混为一谈。
