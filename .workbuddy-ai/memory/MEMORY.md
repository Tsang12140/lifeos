# LifeOS 项目长期记忆

## 预览服务：必须常开，不要当临时进程清理

**主人的要求（2026-09-16 明确纠正过一次）**：

- `.review/accept-serve.mjs` 拉起的**预览服务（API 3011 + Web 5199）是常驻的**，主人随时会打开 `http://127.0.0.1:5199/` 看效果。
- **任务收尾时不要把它杀掉。** 我曾把它当成"临时残留进程"在结束前 taskkill 掉，导致主人下次进不去 5199，被明确纠正。这是失误，不是稳妥。
- **端口固定，不要换。** 没有特殊理由（如端口被主人自己的东西占用）就一直在 3011/5199；即使需要重启，也在**原端口**拉起。
- 主人自己占用的端口（如 3001）**永远不要杀**。
- 真正需要结束的只是**验收/播种用的隔离实例**（如 3021/5299 的 `photo-grid-serve.mjs`）和**临时 Chrome 进程**。

**判断口诀**：`accept-serve.mjs` = 常驻预览，留着；`photo-grid-serve.mjs` 等带隔离 data dir 的 = 验收用完可收。

**但沙箱会在 turn 结束时回收它（2026-09-16 20:30 实测）**：

- `nohup … &` 和 `spawn({ detached: true }).unref()` **都不管用** —— `.review/run/api.log` / `web.log` 里能看到服务确实起来过、随后端口就空了。**只有后台任务机制（Bash 工具的 `run_in_background`）能跨工具调用存活，但它活不过 turn 边界。**
- 所以**每次开工先探一次端口**（`http://127.0.0.1:3011/api/health` + `5199/`），不在就先拉起再跑验收。`.review/spawn-serve.mjs` 是便捷拉起器（已存在就跳过、否则拉起并轮询就绪）。
- **教训**：验收脚本的前置条件分支会**覆盖**上一次的完整结果文件 —— 有一次 3011 没起来，`RESULT: PASS (189 checks)` 被冲成了 2 行前置失败。跑之前先确认预览在线。

## 天气天空的两根轴（2026-09-16 重做）

- `WeatherBackground.tsx` 接两个 prop：`category`（形态，来自预报 `iconDay`）决定**画什么**，`phase`（时段）只决定**什么色、光在哪**。时段是纯 CSS 变量替换 → **加时段不增节点、不增动画**。
- `phase` 由 `getWeatherPhase()` 用**真实日出/日落**算（和风 7d 的 `sunrise`/`sunset`，此前被丢弃）；非今天的日期一律中性 `day`。
- **硬预算（验收脚本 `verify-weather-art.mjs` 在守）**：每形态 ≤ 20 节点；只许动 `transform` / `opacity`；`filter` 只出现在 `cloud--far` / `fog-band` / `lightning-bolt`；`.weather-header *` 里 `backdrop-filter` 必须为 0。
- **`.weather-header-summary` 是 `margin-left: auto`，文字右缘在卡片宽度的 0.917** —— 白蒙版在任何有文字的地方都必须 ≥ 0.5 alpha。放松蒙版前先量文字位置，别猜。
- `cloudy` 分支在真实和风码表下**不可达**（101/102/103/151/152/153 → `partly-cloudy`，104/154 → `overcast`）。

## 动画铁律：不许有「移动的细周期图案」（2026-09-16 21:45 主人报障）

- **症状**：雷阵雨表头「有很重的摩尔纹，晃眼睛」。
- **根因**：雨幕是 10px 周期条纹、以 226px/s 平移 = **每秒 22.6 个周期**，两张幕周期还不同（互相拍频），再加 14° 旋转的重采样。
- **结论（刻死）**：
  1. **「数学上无缝」≠「视觉上没问题」**。`rotate(θ) + translate3d(n·period)` 确实像素级无缝，但**无缝只解决接缝跳变，解决不了 aliasing**。
  2. **要密度就用非周期或静态的东西**：雨线位置 `(index*97)%100` 步进互质 → 非周期 → 实测在噪声本底；或者用**静态**纹理（不动就不会闪）。**永不恢复移动的条纹幕布。**
  3. 同类风险：任何 `repeating-linear-gradient` / 细网点 / 摩尔纹格，只要**在动**且周期小，都要先量。
- **量化守卫**：`.review/verify-weather-art.mjs` 第 7 段（内嵌 PNG 解码 + 高频能量 `mean|L(x+1)-L(x)|`）。断言：无 `.rain-sheet`、`.weather-bg` 内无 `repeating-` 背景、雷阵雨高频能量 ≤ 小雨基线 × 1.35。
- **量像素的两个前提**：① **必须只量无文字带**（文字边缘的高频能量远大于任何图层，整卡测量会让基线失效）；② `document.getAnimations().forEach(a => a.pause())` 让采样确定化。探针见 `.review/probe-sheet-moire.mjs`。

## CSS 动画的两个默认值陷阱（2026-09-16 22:15）

1. **`animation-fill-mode` 默认 `none`，正 `animation-delay` 期间元素按「基准样式」渲染**，不是隐藏等待。
   → 任何"从屏幕外飞入"的元素，**基准位置本身必须在屏幕外**；只把关键帧起点写到屏幕外**不够**。
   → 更好的做法是**用负延迟**（动画第一帧就在进行中，错峰保留、没有等待期）。两者一起用最稳。
   （实例：雨滴 `top: 0` + 正延迟 → 静止挂在卡片顶端；雪花同样。已修 `top: -30px` + 负延迟。）
2. **验"元素不跳动"别只信 CLS**：规范排除**用户输入后 500ms 内**的位移（`hadRecentInput`），而脚本 `.click()` 不算真实输入 → 结果失真。
   **逐元素比 `getBoundingClientRect()` 前后值**才是硬证据（本次六项元素矩形逐字节一致）。

## 天气层的结构（2026-09-16 22:15 起）

- `WeatherHeader` 用 **`WeatherSky`**（不是直接用 `WeatherBackground`）：`shown` / `outgoing` 两槽位做**交叉溶解**。
- **旧层叠在最上淡出，新层在下面就位** —— 因为两层天空各只有 0.8 透明度，反向叠会让过渡中段互相稀释被白底冲淡（发灰）。
- `.weather-bg-layer` 在 `.weather-bg` **外面**，所以不影响验收里的节点预算计数。
- 刷新键的 spinner 由 **`manualBusy`** 驱动，**只有手动按刷新才转**（切日期走自动刷新，不闪）。

## 验收要点（详见 AGENTS.md）

- **当前模型读不了图**，视觉验收只能靠 CDP 客观断言（`getComputedStyle` / `getBoundingClientRect` / 元素计数），截图给主人自己看。
- **`transform` 不改变布局盒宽**：用 `translateX` 做元素叠压，元素的布局总宽仍然是「N 个元素的宽度」，会溢出让容器外；而 `documentElement` 的横向溢出可能是 0（页面够宽吃掉了），**光看页面级溢出会漏掉泄漏**。要用负 margin 参与布局，并逐元素对容器边界断言。
- 旋转/变换后的元素**画出来比布局盒宽**（`w·|cos| + h·|sin|`），预留 overhang。
- 跑 CDP 脚本时若要切换视口，**量不同形态前记得 `Emulation.clearDeviceMetricsOverride`**，否则会量到上一个视口的折叠态几何（曾导致 5 项假 FAIL）。
