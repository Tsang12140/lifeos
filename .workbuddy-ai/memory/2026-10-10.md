## 补充 6：阶段 2 前置实验（二）—— 选项 D 实测，**D 被证伪**

我上一轮倾向 D，依据是「node-llama-cpp 的平台件走 optionalDependencies，npm 只装匹配本机那个，约 70 MB」。
**实测把这个估计证伪了。**

- **默认安装 676.1 MB**（transformers.js 才 373.4 MB）。原因：5 个 win 包**全部声明 `os:["win32"] cpu:["x64"]`**，
  对本机全部合法匹配 → 全装。`win-x64-cuda-ext` 350.9 + `win-x64-cuda` 167.9 + `win-x64-vulkan` 70.9 +
  `win-arm64` 10.5 + `win-x64` 29.3（**只有这个是真正要用的**）+ 本体 37.8。
  ⇒ **可选依赖 ≠ 平台过滤**；它们是同 OS 不同加速后端的并列候选，不是跨 OS 死重。
- **剪裁后 75.9 MB，但会改结果**：未剪裁 r@1 **67%**（2/2 一致）→ 剪裁后 **75%**（2/2 一致）。
  翻盘的是 q02，e03 与 e29 只差 **0.0007**。⇒ 后端选择会微调数值，足以翻转毫厘之争。
- **确定性专项**：同 context 重复 / 批量后重算 / 两个独立实例，**最大逐位差全 0.000e+0**。
  ⇒ 不是随机抖动，环境固定则确定。
- **GGUF 有官方 tokenizer 告警**（`special_eos_id is not in special_eog_ids` +
  `tokenize then detokenize resulted in a different text … may not work as intended`）。
- **WASM 不是出路**：`onnxruntime-web` **89.6 MB**，比剪裁后的 `onnxruntime-node`（67.2 MB）**还大**。
- **C（ONNX 剪裁）已验证干净**：只移 `bin/napi-v3/{darwin,linux}` → **232.8 MB**，
  **语义平均分差 0.0638 未变**、r@1/r@3 一致。
- **建议改为 B+C**：transformers.js + Xenova/bge-small-zh-v1.5，剪 darwin/linux → **255.7 MB**。
- **踩坑（重要）**：① **首轮速度数字全不可信** —— 首测「54.5 ms/篇、396 ms/查询」，热机重测 **8 / 2.7 ms**，
  差 7 倍（冷启动 + 刚下载完文件抖动，**不是缓存**）。**报速度前必须热机重跑。**
  ② Node 里 `fetch(...).body` 是 Web ReadableStream，没有 `.pipe()` → 用 `Buffer.from(await res.arrayBuffer())`。
  ③ 剪裁别用 `rm`（safe-delete 闸门，删 350 MB 上千文件必被拒）→ `mv` 到 `_pruned/`。
- 证据：`.review/semantic-model-decision.txt` + `.review/semantic-experiment/llama/`。

## 19:05 搜索框 demo：「右侧满高」改成**相对规格**（主人纠正：demo 的物理边缘 ≠ 真实 app）（在下 / WorkBuddy）

**主人原话**：「你可要记得，你现在在 demo 页面做的那些物理边缘跟咱们真实的那个是不一样的。
所以你可能从相对的角度去出发比较好。」—— 说得对，我上一轮量的是 **demo 自己的边缘**
（`.demo-bar` 控制条高度、`#feed` 右缘、拍脑袋的 `width:380px`、`距控制条 210px`），**搬到真实 app 全是错的**。

**做法：把判据从「绝对像素」换成「相对布局容器」。** 读了真实布局：
```
apps/web/src/styles.css:1206 .content-grid { grid-template-columns: minmax(0,780px) 246px;
                                            gap: clamp(28px,5vw,76px); max-width:1160px }
              :7223 @media(max-width:1160) { .content-grid{ minmax(0,1fr) 214px; gap:34px } }
              :7235 @media(max-width:900)  { .content-grid{ display:block; max-width:780px } }  ← 侧栏隐藏
```
⇒ **右侧带**（内容列右缘 → 右侧栏右缘）= `gap + 栏宽 − 12`：
**>1160 = 262~310px｜901~1160 = 236px｜≤900 = 0（没有带 ⇒ 必须退化）**。

**落进 demo 的相对规格**（`search-box-demo.html`）：
- 四条边全由 JS 从 `.wrap`/`.content-col`/`.rail` 量出，**不写死像素**：
  `左缘 = 内容列右缘 + 12`｜`右缘 = 右侧栏右缘`｜`顶缘 = 固定头栏下沿 + 16`｜`底缘 = 视口底 − 16`
- 改成 **`position:fixed`**（锚视口，和「面板嵌在哪层 DOM」无关）—— 顺带不再需要 `.pill{overflow:visible}`
- 窄屏退化：带宽 < `POP_MIN_BAND` ⇒ 底部抽屉（左右 16、贴底、≤70vh）
- **demo 的 `.wrap` 网格规格改成与真实 app 逐字一致**（`gap:clamp(28px,5vw,76px)`；手机模式 `display:block;max-width:780px`）
  —— 否则「相对规格」只是看起来对：实测改完 demo 量到 **310px = 真实 app 投影 310px**。

**踩到的坑**：
1. **`POP_MIN_BAND` 一开始取 240 ⇒ 会把真实 app 的「901~1160 带宽 236」误判成「没有右侧带」**
   → 改 200。**阈值必须从真实断点反推，不能拍**。
2. **窄屏退化原锚 `.app-frame`** —— 但 demo 的 `.app-frame` 被 `.app-frame{flex:1}` 撑满
   （`width:390px` 被 `flex-basis:0` 压掉，**demo 手机模式的「手机框」从来就没生效过**，既有问题非本轮引入）；
   而且固定定位的面板**本就该锚视口** → 改用 `innerWidth/innerHeight`。
3. 断言「抽屉零相交」是**错的量尺** —— 底部抽屉必然盖住列表底部。改成断言
   **「抽屉顶缘在搜索框下方（搜索框仍可见）」** + 高度 ≤70vh，相交数只记录不断言。

**验收**：`.review/verify-popover-up-position.mjs` **32/32 PASS**（六个阶段：右侧向上 / 下方对照 /
药丸内不被裁 / 向上不压侧栏 / 满高（含 760px 窄屏退化）/ 真实断点投影），
`.review/verify-popover-up-position.txt` 末行 `RESULT: PASS`；profile 回收 0 新增。

## 20:40 搜索框 demo：主人否掉「顶天立地」→ 高度改自适应 + 落地分组折叠（在下 / WorkBuddy）

**主人原话**：「我想要的是右侧 搜索旁边 高度给够 但是不是顶天立地」。上一轮我做的是
`顶缘 = 头栏下沿 + 16` → `底缘 = 视口底 − 16`，**那正好就是顶天立地**，理解偏了。

**关键判断**：光把 `height:var(--pop-h)` 改成 `height:auto` **没用** —— 内容本身有 866px，
`auto` 还是会顶到底。**要真做到「不顶天立地」必须把分组折叠起来**（两轮前就写了「无论选哪个
方案都得做」的那条）。

**新相对规格**（`search-box-demo.html`，位置标签改名「右侧自适应」）：
- 左缘 = 内容列右缘 + 12 ｜ 右缘 = 右侧栏右缘 ｜ 宽 = 右侧带宽（不变）
- **顶缘 = 搜索框顶缘**（与搜索框同高起头 = 「搜索旁边」）
- **高 = 内容自然高度（`height:auto`）**，上限 = `max-height: 视口底 − 16 − 顶缘`
  ⇒ 内容少就矮、内容多才滚动，**不硬撑到视口底**

**分组折叠**：`.row`/`.more` 那套换成统一 `.sec` + `.sec-head` + `.sec-body` 四组
（记录类型 / 人物 / 时间 / 更多条件）。默认只展开第一组。**收起的组在标题行右侧显示已选摘要**
（`#valKind`/`#valPerson`/`#valTime`/`#valMore`，时间会识别出「近 7 天」这类预设）
⇒ **收起 ≠ 看不见自己选了什么**。点标题行开合后要 `syncPopGeom()` 重算几何。

**实测数字**（视口 1680×950，内容列 780 / 侧栏 246 / gap 76）：
| 状态 | 面板高 | 底缘距视口底 |
|---|---|---|
| 默认（只开「记录类型」） | **309px** | **409px** ← 不顶天立地 |
| 全展开 | 702px（被上限夹住，内部滚动：内容 727 > 可视 700） | 16px |
| 全收起 | 265px | 453px |

**顺带证伪一条我自己的猜想**：以为「面板要贴搜索框右边」⇒ 搜索框宽度变了面板就得跟着变。
实测**搜索框 762 右缘 → 982 右缘，面板左缘始终 1073、宽始终 310** —— 因为锚的是**内容列**，
不是搜索框右缘。**这条写进验收（5.4），是「相对规格」价值的直接证据。**

**踩到的坑（都是量尺，不是产品）**：① `setSecs("none")` 我给「全收起」传的是「默认」那张表
⇒ 根本没关（`展开 1/4`），「比默认更矮」假 FAIL；② 「高度严格跟随内容」在**全展开时不成立**

**判据要分「夹住」和「没夹住」两种情形写，不能一句话通吃。**
